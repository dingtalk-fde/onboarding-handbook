# Git 分支模型与开发流程

> 文档负责人：质量与效能部 孙蕾｜最近更新：2026-08-25

## 分支模型（简化的 GitLab Flow）

| 分支 | 说明 | 保护规则 |
|------|------|----------|
| `main` | 主干，始终可发布；生产发布从 main 打 Tag | 受保护，只能通过 MR 合并，禁止 force push |
| `feature/<jira号>-<简述>` | 功能开发分支，从 main 拉出 | 合并后自动删除 |
| `fix/<jira号>-<简述>` | 普通缺陷修复 | 同上 |
| `release/<版本号>` | 仅移动端和私有化交付项目使用，用于版本冻结 | 受保护 |
| `hotfix/<jira号>-<简述>` | 生产紧急修复，从线上 Tag 拉出 | 需走紧急发布流程 |

示例：`feature/CRM-5102-points-expire-notify`

## 标准开发流程

1. **需求**：在 Jira 认领需求或缺陷，状态改为“开发中”。
2. **技术方案**：中等以上需求（≥ 3 人日）需写技术方案（Confluence 模板“技术方案 v3”），由组长评审；跨团队或涉及新组件的需要架构评审。
3. **开发**：从 `main` 拉 feature 分支，本地开发并自测，频繁提交。
4. **提 MR**：推送分支，创建 MR 到 `main`，填写 MR 模板（变更说明、测试方式、影响范围、回滚方案）。
5. **CI**：自动执行编译、单测、代码扫描、构建镜像，并部署到 dev 环境。
6. **Code Review**：见[代码评审规范](code-review.md)。
7. **测试**：测试工程师在 test 环境验证，Jira 状态流转到“待发布”。
8. **合并与发布**：MR 合并后，按[CI/CD 与发布流程](ci-cd-release.md)发布到 staging 和 prod。

## 规则

- **禁止直接向 `main` 推送**，包括组长和管理员。
- MR 合并方式统一为 **Squash and merge**，保持主干历史清晰。
- 分支存活不超过 2 周，长期分支需要定期 rebase main。
- 禁止提交大文件（> 10MB）、二进制产物、`.env` 文件、IDE 配置；仓库根目录必须有 `.gitignore`。
- 提交身份必须是公司邮箱，CI 会拒绝非公司邮箱的提交。
