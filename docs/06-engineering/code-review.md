# 代码评审（Code Review）规范

> 文档负责人：沈默、叶知秋｜最近更新：2026-08-25

## 审批人数要求

| 仓库级别 | 示例 | 需要的 Approve 数 |
|----------|------|-------------------|
| 核心仓库（L1） | NAP 运行时、模型网关、电商平台连接器、权限与租户隔离、涉及退款/改价等资金动作的工具 | **2 个**，其中至少 1 个为模块 Owner 或组长 |
| 普通仓库（L2） | 客户项目仓库（Agent 配置、Prompt、工具代码）、客户控制台前端 | **1 个** |
| 工具/文档仓库（L3） | 脚本、文档、内部工具 | 1 个（可由同组任何人） |

- 作者不能批准自己的 MR。
- 涉及数据库 DDL 的 MR，必须附上 Launchpad 数据库变更工单链接。
- 涉及权限、加解密、个人信息处理的代码，需 @信息安全组 周子涵 评审。

## 时效

- Reviewer 应在 **1 个工作日内**给出首次反馈；紧急修复 2 小时内。
- MR 超过 2 个工作日无人评审，可在团队群提醒或找组长指派。

## 评审要点

1. **正确性**：逻辑是否正确，边界条件、并发、幂等是否考虑。
2. **可读性**：命名、结构、注释是否清楚。
3. **测试**：是否有足够的单元测试，测试是否真的在验证行为。
4. **安全**：输入校验、越权（客户租户 tenant_id 隔离）、敏感信息日志、SQL 注入、**Prompt 注入**（消费者输入不能改变 Agent 的系统指令或触发越权工具调用）。
5. **性能**：N+1 查询、大循环中的远程调用、缓存使用。
6. **兼容性**：接口和数据结构变更是否向后兼容，是否有灰度方案。
7. **Prompt 与评测**：Prompt 变更必须附 NEval 回归报告链接；Reviewer 要检查 Guardrail 是否被削弱、Badcase 是否已加入评测集。

## 评论约定

用前缀标明评论的分量，减少误解：

- `[必须]`：必须修改后才能合并
- `[建议]`：建议修改，作者可自行决定
- `[疑问]`：需要作者解释
- `[nit]`：小问题（格式、拼写），不阻塞
- `[赞]`：写得好的地方，也请说出来

## 礼仪

- 对事不对人：说“这里可能会有并发问题”，而不是“你写错了”。
- 有争议时，超过 3 轮评论没有结论，改为当面或语音沟通，然后把结论写回 MR。
- 新人的 MR 请 Reviewer 多写一句“为什么”。
